# AGENTS.md

## Learned User Preferences

- Commits, MRs e comunicação geral em português (pt-BR); alinhar implementação ao design system DaisyUI e regras NestJS/TS do projeto
- UX mobile-first em listagens e formulários — tabelas em cards no mobile, modais e fluxos pensados primeiro para telas pequenas; no app Expo, evitar `SafeAreaView` com inset superior duplicado em telas filhas quando o layout `(app)/_layout` já aplicar safe area no topo
- Modais com cabeçalho e rodapé fixos, scroll vertical no conteúdo, botão fechar visível e confirmação ao descartar alterações somente após interação real do usuário
- CRUDs administrativos no web seguem a skill `crud-frontend` (`CrudFiltros` + `CrudTable`): filtros com Pesquisar/Limpar, listagem com menu de ações e carga inicial ~20 registros; a tabela usa o mesmo card visual dos filtros e o menu de ações não pode ser cortado por overflow (posicionamento fixed + getBoundingClientRect)
- Copy de landing/páginas públicas (`apps/web/src/app/page.tsx`): tom sóbrio e funcional focado no que o sistema faz, sem apelação/marketing exagerado, sem mencionar o público-alvo e sem jargão de TI (RAG, OTP, API, CRUD, SQLite, offline-first, tokens) — usar linguagem natural do usuário
- Interfaces de checklist: tooltips em todas as ações, ícones sempre visíveis (não só hover), botões `btn-square`, ordem: duplicar → editar → remover; exclusões com `ConfirmDialog`, não `confirm()` nativo
- PDFs e downloads: preferir abrir/visualizar no navegador (nova aba) quando a intenção for "ver o arquivo"; tratar bloqueio de pop-up com orientação ao usuário e download manual; durante geração de PDF de relatório, usar overlay de carregamento em tela cheia alinhado ao padrão visual dos modais
- Fotos em itens de auditoria: permitir múltiplas seleções, upload e processamento de IA em sequência (não paralelo), feedback visual imediato, grid de duas colunas no mobile
- Para mudanças de schema no banco, preferir scripts SQL em `scripts/` em vez de migrations do TypeORM
- Isolamento e autorização de dados devem ser garantidos na API (não só no front); regras de vínculo gestor/consultor/tenant prevalecem para todos os perfis
- Ocultar o FAB de check-in/checkout nas áreas de checklist, auditoria e relatórios para evitar controles duplicados
- Quando funcionalidade envolver IA, respeitar auditoria de tokens e regras do projeto (`.cursor/rules/auditoria-tokens.mdc`)

## Learned Workspace Facts

- Monorepo: API NestJS em `apps/api`, frontend Next.js em `apps/web`, app mobile Expo em `apps/mobile`, UI com DaisyUI/Tailwind no web; em desenvolvimento local o Next usa a porta 3031 (`next dev --port 3031`) para não colidir com Langfuse ou o padrão 3000 — README/CORS e exemplos locais costumam apontar para `http://localhost:3031`; componentes compartilhados em `apps/web/src/components/ui/` (form-modal, crud-table, crud-filtros, overlay de loading em PDF); geração de PDF de relatórios na API com Puppeteer/Chromium (Docker) e preparação de imagens com sharp; variáveis opcionais `CHEKAI_LOGO_URL` e `PDF_GERACAO_METRICAS`; PWA offline completo abandonado em favor de API direta; skills em `.cursor/skills/` (ex.: crud-frontend) e subagentes em `.cursor/agents/` (ex.: skill-architect, use-case-driven-dev, business-rules-expert, sdd-use-case-generator, mobile-expert, platform-orchestrator); observabilidade do Cursor com Langfuse via hooks em `.cursor/hooks/` (variáveis `LANGFUSE_*` no `.env`); build nativo iOS: em macOS recentes o Ruby do sistema pode quebrar o CocoaPods — usar Ruby Homebrew para `pod install`; pode ser necessário workaround do pod `fmt`/Clang no `Podfile` com Xcode muito novo (patch via `post_install` no `base.h` definindo `FMT_USE_CONSTEVAL 0`); o web sobe com `next dev --port 3031 --hostname 0.0.0.0`, então o browser envia `Origin: http://0.0.0.0:3031` e o CORS da API (`apps/api/src/main.ts`) deve liberar origens locais de dev (`localhost`, `127.0.0.1`, `0.0.0.0` em qualquer porta); o app iOS real é `apps/mobile/ios/chekAI.xcworkspace` (scheme `chekAI`) — o projeto nativo órfão `ios/metaapp.xcodeproj` da raiz foi removido (autolinking incompleto, sem `ExpoLinking` → buildá-lo causava tela preta); para Archive/TestFlight via Xcode os ajustes vão no projeto nativo (`Info.plist`: `ITSAppUsesNonExemptEncryption=false` para export compliance e `CFBundleVersion` incremental), não só no `app.json`, e evitar `prebuild` para não sobrescrever a splash nativa
- Pipeline de desenvolvimento SDD: todo desenvolvimento que altere comportamento passa por `platform-orchestrator` → `business-rules-expert` (valida regras em `docs/regras-de-negocio.md`) → `sdd-use-case-generator` (gera UCs rastreáveis) → `use-case-driven-dev` (TDD a partir da Fase 2) → `mobile-expert` (se mobile) → `skill-architect` (captura padrões); regras de negócio catalogadas com IDs `RN-XXX-NNN`; matriz de paridade web/mobile em `docs/paridade-plataformas.md` e DE:PARA funcional (mesmas APIs/params/relations) em `docs/de-para-web-mobile.md`
- Isolamento de dados combina `gestorId` (clientes, checklists, usuários) e `consultorId` (auditorias, relatórios técnicos); JWT enriquecido e `@CurrentUser()` injetam contexto; padrão gestor vê recursos dos auditores vinculados
- Perfis de usuário: MASTER, GESTOR, AUDITOR (enum `PerfilUsuario`); fluxo de criação por convite, enum `StatusUsuario`, OTP só para conta ativa após aceite
- Checklist: templates com status rascunho/ativo/inativo, geração com IA via `IaService`, RAG via legislação e auditoria de tokens (`CreditoService`); no mobile a tela de templates deve listar TODOS os ativos sem filtrar por `tipo_atividade` do cliente/estabelecimento (igual ao web) e o fluxo de nova auditoria segue Cliente → Unidade → Checklist
- Relatório técnico é por cliente (sem auditoria/pontuação), com wizard/pré-criação, apoio analítico gerado por IA (somente leitura), evidências fotográficas sem IA nas imagens
- Check-in: AUDITOR, GESTOR e MASTER podem usar; checkout exige `ConfirmDialog`; filtros de auditor/cliente refletem apenas o vínculo da conta
- E-mail: em produção (Railway), SMTP em portas clássicas dá timeout — usar provider HTTP (Resend, MailerSend ou SendGrid via HTTPS/443) conforme `EMAIL_PROVIDER`; em dev, Ethereal via `nodemailer.createTestAccount()`; `FRONTEND_URL` é obrigatória em todos os ambientes (sem fallback para localhost — falhar claro se faltar) e os templates HTML de e-mail devem constar em assets no `nest-cli.json` para irem ao `dist` no build
- Mobile (Expo): `crypto.randomUUID()` NÃO existe no runtime React Native — usar `expo-crypto` centralizado em `src/utils/uuid.ts` (`gerarUUID()`); o app usa `react-native-mmkv` (lib nativa), incompatível com Expo Go, então rodar sempre como development build (`expo start --dev-client` / `expo run:ios`) — o script `start` já força `--dev-client`; a `baseURL` da API é resolvida em `src/api/config.ts` e usa `EXPO_PUBLIC_*` (embutida no bundle em build time), na ordem `.env.local` (dev) → `expo.extra.apiUrl` no `app.json` (produção, versionado) → fallback localhost — como `apps/mobile/.env` é gitignored, a URL de produção (`https://api.chekai.com.br/api`) fica embutida via `expo.extra.apiUrl` para builds standalone/EAS não caírem no localhost; splash nativa com fundo branco, ícone reduzido e logo animada (Reanimated, componente `AnimatedSplash`)
- TypeORM: salvar entidade após carregar relação filtrada pode anular FK nos filhos — atualizar metadados sem persistir array incompleto; respostas binárias ou stream na API (ex.: PDF): interceptores globais não devem envolver em JSON quando `res.headersSent` ou quando o handler já enviou o corpo / `StreamableFile`
- Sincronização mobile de auditorias: a listagem `GET /auditorias` na API deve incluir a relação `itens` para o pull offline popular `auditoria_itens` no SQLite (sem isso o checklist pode ficar vazio após sync); o pull de listagem descartava auditorias cujo `template` não estava local (a API só sincroniza templates ativos, mas auditorias podem usar templates inativos/rascunho) — corrigido hidratando um stub do template a partir da própria resposta, e ao abrir a auditoria hidratar o detalhe completo via `getAuditoriaDetalhe` (`GET /auditorias/:id` → template + itens com `templateItem` + fotos) de forma idempotente/offline-first (sem sobrescrever respostas/fotos `pending`), espelhando o web
- MemPalace MCP no projeto: wing `chekai` (rooms: `architecture`, `decisions`, `ux-patterns`, `bugs`, `features`, `platform-parity`); protocolo de uso em `.cursor/rules/mempalace.mdc` para memória persistente entre sessões; gestão de tarefas de desenvolvimento via MCP do ClickUp (servidor remoto OAuth `https://mcp.clickup.com/mcp` em `.cursor/mcp.json`), workspace `90171280664`, list de desenvolvimento `Projeto 1` (`901714172692`)
